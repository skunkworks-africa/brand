Components / 1.0

Help people get it right.

Visible labels, useful hints, validation and recoverable errors.

Interactive example

Use the name you would like us to use.Enter your name to continue.

This local example validates a name and sends no data. Add application validation on the server as well as in the browser.

Code

<form id="example-form" novalidate><div class="sk-field"><label for="example-name">Your name</label><input class="sk-input" id="example-name" name="name" autocomplete="name" required aria-describedby="name-hint name-error"><span class="sk-hint" id="name-hint">Use the name you would like us to use.</span><span class="sk-error" id="name-error" hidden>Enter your name to continue.</span></div><div class="sk-field"><label for="example-discipline">Discipline</label><select class="sk-input" id="example-discipline" name="discipline"><option>Design</option><option>Engineering</option><option>Content</option></select></div><label class="sk-check"><input type="checkbox" name="updates"> Include the optional design update</label><button class="sk-button" type="submit">Validate example <span aria-hidden="true">→</span></button><p id="form-result" role="status"></p></form>

Basic usage

  • Use visible labels; placeholder text does not replace a label.
  • Link hints and errors using aria-describedby. Set aria-invalid only after validation fails.
  • For long forms, add an error summary linking to each invalid field.
  • Use autocomplete and appropriate input types. Make optional fields explicit.
  • Do not collect sensitive information without a defined purpose, retention period and secure service.

Anatomy of a helpful field

Give every control a persistent, visible label. Put concise instructions before the control where they help someone answer, and place an actionable error beside the field after validation. State which fields are required; mark optional fields explicitly when most fields are required.

Helpful

Work email (required)
We’ll use this address to reply.
Enter an email address in the format name@example.com.

Unhelpful

A placeholder as the only label, or an error that says only “Invalid input”.

    Use the example in your project

    Load tokens.css and components.css, copy the example markup above, and adapt the validation example JavaScript ↓. The script is scoped to this form and uses its IDs; change the markup and script together when integrating it. Provide a working server-side submission and validation flow in your own application.

    Validation and recovery

    • Validate on submission; avoid showing errors before the person has had an opportunity to answer. Recheck fields after an unsuccessful submission as they are corrected.
    • When there are multiple errors, show an error summary near the start of the form, focus it after submission and link each message to its field.
    • Set aria-invalid="true" only for fields that fail validation. Associate hints and error messages with aria-describedby; keep messages specific and actionable.
    • Preserve all entered values and selections after a validation or service error. Explain the problem and provide a realistic next step.
    • Validate again on the server. Client-side checks improve feedback but cannot enforce security or guarantee that an address exists.
    • Do not depend on colour alone; use visible error text, and check focus and contrast in both themes.

    Choosing and designing fields

    • Use native email, telephone, select, textarea, checkbox and radio controls with an appropriate input type, autocomplete token and keyboard support.
    • Group related radio buttons or checkboxes with fieldset and legend. Use radio buttons for one choice and checkboxes for independent choices.
    • Use inputmode, patterns and limits only when they reflect real requirements; do not reject valid international names or telephone formats without a documented reason.
    • Keep labels visible after typing. Do not use a placeholder as the only label or a preselected optional marketing checkbox.
    • Explain why information is needed and provide the relevant privacy notice before collecting it. Protect submitted data and define retention in the application.
    • Test with keyboard, screen readers, 200% zoom, small screens and long translated labels. Automated checks do not replace user testing.
